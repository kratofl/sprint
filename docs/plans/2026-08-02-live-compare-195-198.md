# Live Compare #195–#198 Implementation Plan

**Goal:** Finish epic #193 on top of the landed channel trace (#194): a HUD over the game, an Analysis view, lap files, and cloud share codes.

**Architecture:** One shared core turns traces into `ChartStack`s (`Features/Charts/LapTraceCharts.cs`), so the HUD and the Analysis view render the same way through the already-built, Avalonia-free `ChartStackPainter`. One shared codec (`LapTraceCodec`) serialises a trace, used by the local store, the lap file, and the cloud blob. One shared receiving path (`SharedLapImporter`) files a third-party lap, used by both file import and cloud fetch.

**Tech Stack:** .NET 10, Avalonia, SkiaSharp, xunit v2, Win32 P/Invoke (`user32`, `shell32`), HotChocolate GraphQL, EF Core/Postgres. **No new dependencies.**

## Global Constraints

- Spec `docs/specs/live-compare.md` is settled. Do not re-derive it.
- `-warnaserror` clean; full desktop suite green; visual smoke + UI review PNGs inspected before any UI claim.
- Every Win32 call guarded by `OperatingSystem.IsWindows()`, following `WindowsRawInputSource` and `WinUsbInterop`.
- Avalonia-free cores for everything testable; Avalonia only in the window/page shells.
- Keep logic out of `MainWindow.cs` (5,483 lines already) — new features get their own files under `Features/`.
- Contract changes mirror to `packages/types`; `make schema` re-exports `web/schema.graphql`.

## Build order (deviates from spec §4, deliberately)

Spec §4 orders HUD → Analysis → Cloud → File by *dependency*. Two swaps, for build reasons only, no design change:

1. **Shared chart core first.** Both #195 and #196 need "trace → `ChartStack`". Writing it once, tested, before either host.
2. **File (#198) before Cloud (#197).** The cloud blob *is* the lap file, and both need the same receiving path. Building the file format first means the cloud step is transport only.

Order: **core → #195 HUD → #196 Analysis → #198 file → #197 cloud.**

## Task 1 — Shared chart core

**Files:** create `Features/Charts/LapTraceCharts.cs`, `Features/Charts/LapChartPanels.cs`; modify `Features/Charts/ChartDomain.cs`, `ChartStackPainter.cs`, `ChartPalette.cs`; test `LapTraceChartsTests.cs`.

**Produces:**
- `ChartDomainKind.TrackDistance` + `ChartDomain.TrackDistance(double fromMeters, double toMeters)`
- `sealed record LapChartPanelSpec(string Id, string Title, string? Unit, IReadOnlyList<string> Channels, bool FillFirst)`
- `static class LapChartPanels` — `Speed`, `Pedals`, `Steering`, `Gear`, `All`, `HudDefaults`, `AnalysisDefaults`, `ById(string)`
- `static class LapTraceCharts` — `ChartStack Build(IReadOnlyList<LapChartPanelSpec> panels, ChartDomain domain, LapTraceSeriesSource? current, LapTraceSeriesSource? comparison)`
- `readonly record struct LapTraceSeriesSource(LapChannelTrace Trace, double TrackLengthMeters, double? UpToPosition, ChartSeriesRole Role)`
- `ChartStackPainter(int width, int height, SKColor? background = null)`

**Decisions:**

- **A distance domain, not a fraction.** The HUD window runs from `position - behind` to `position + ahead` in metres. On the existing `TrackPosition` domain that reads "105.2%" past the line and the numbers mean nothing to a driver. Metres is what the spec says the reading is.
- **The target series wraps, your series does not.** Past the line the target keeps drawing because the whole lap is on disk; your own line stops at your current position. That asymmetry is spec §3, accepted, and the HUD is built around it rather than hiding it. Target samples are looked up modulo track length and plotted at unwrapped X, so the window scrolls continuously through the start/finish line.
- **Throttle and brake share one panel, told apart by fill, not colour.** Colour keeps meaning whose lap it is (ember/blue). `FillFirst` fills the *first* channel in the spec's list — brake is listed first so the filled shape is the braking trace, which is what a driver is shaping.
- **The painter takes a background colour.** Today it hard-clears to `ChartPalette.Surface`, opaque. The HUD needs to see the game through it. One optional constructor argument, default unchanged.

- [ ] Add `TrackDistance` to `ChartDomainKind`, the factory, `Label` ("Track distance"), `AxisLabel` ("Distance"), and `Format` → `"1250 m"`.
- [ ] Add the optional `background` argument to `ChartStackPainter` and use it in `Render`'s `Clear`.
- [ ] Add `ChartPalette.HudSurface` — `Graphite.Panel2` at ~78% alpha, plus `HudPanel` for a slightly stronger plot backing so a light game frame cannot wash the lines out.
- [ ] Write `LapChartPanels` and `LapTraceCharts.Build`, sampling each trace channel across the domain onto `ChartSample(distanceMeters, value)`.
- [ ] Tests: distance domain formats and ticks; two sources produce ember + blue; `UpToPosition` truncates the current series and leaves the comparison whole; the target wraps past the line; an absent channel yields an `Empty` panel rather than a flat zero line; pedals panel fills brake only.

Commit: `feat(charts): distance domain and a shared trace-to-stack builder (#195, #196)`

## Task 2 — Live Compare target and rolling window (#195 core)

**Files:** create `Features/LiveCompare/LiveCompareTarget.cs`, `LiveCompareController.cs`, `LiveCompareSettings.cs`; test `LiveCompareControllerTests.cs`.

**Produces:**
- `sealed record LiveCompareTarget(string SessionId, int LapNumber, string Label, double LapTimeSeconds, LapHistoryContext Context)` + `TraceId`
- `sealed class LiveCompareController` — Avalonia-free
  - `void SetTarget(LiveCompareTarget? target, LapChannelTrace? trace)`
  - `void Ingest(TelemetryFrame frame)`
  - `ChartStack? Stack { get; }` / `string TargetName { get; }` / `bool HasTarget`
  - `double? DeltaSeconds { get; }`
  - `event EventHandler? Changed`
- `sealed class LiveCompareSettings` on `AppSettings` — `MetersBehind` (200), `MetersAhead` (600), `PanelIds`, `Locked`, `Visible`, `List<HudWindowLayout> Layouts`

**Decisions:**

- **Live Compare owns its target and never reads the armed plan target** (spec §2.4). The HUD's main use is practice with nothing armed, and a plan target routinely resolves to `time only`, which cannot feed a curve at all.
- **Only `full trace` laps are selectable.** A curve has no channels, so it cannot draw speed or pedals. Thinner tiers are listed as unavailable *with the reason*, not hidden.
- **The controller keeps its own live sample buffer**, the same shape the recorder uses, reset on lap change and on leaving the car. It does not reach into `LapHistoryRecorder`: that class exists to write the corpus, and a second consumer of its private buffer would couple the HUD's lifetime to the recorder's.
- **The HUD always names the lap it is chasing** (spec §2.4), because the wheel delta and the HUD can legitimately be measuring different laps.

- [ ] Tests: no target → no stack; a target with a trace and live frames → two series; the current series ends at the car; the window follows the car; leaving the car clears the live line but keeps the target; a lap change resets the live line; delta is read from the target's `elapsedSeconds` channel at the current position.

Commit: `feat(compare): rolling-window controller that owns its own target (#195)`

## Task 3 — The HUD window (#195 shell)

**Files:** create `Features/LiveCompare/CompareHudWindow.cs`, `HudInterop.cs`, `HudLayoutStore.cs`; modify `MainWindow.cs`, `Features/Input/CommandBus.cs`, `Runtime/AppSettings.cs`; test `LiveCompareHudTests.cs`.

**Produces:**
- `static class HudInterop` — `bool SetClickThrough(IntPtr hwnd, bool on)`, `bool IsExclusiveFullscreenActive()`
- `sealed class CompareHudWindow : Window`
- `static class HudLayoutStore` — `string KeyFor(Screen screen)`, save/restore
- `SprintCommands.CompareHudToggle = "compare.hud.toggle"`

**Decisions:**

- **Exclusive fullscreen is detected with `SHQueryUserNotificationState`**, not by comparing window rects. A borderless-fullscreen game also fills the monitor, and that case works fine — rect comparison would produce a false warning on the configuration we actually support. `QUNS_RUNNING_D3D_FULL_SCREEN` (3) is exactly the state that hides a topmost window.
- **Locked sets `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE`** so clicks and focus pass through and the HUD cannot be nudged or steal focus mid-corner.
- **Lock and target live in the Sprint window only** (spec §2.5) — a locked HUD is click-through, so an unlock button on it would be unreachable.
- **Layout key is `{x},{y}@{w}x{h}`** of the screen bounds. A monitor index is not stable across replug; bounds identify the monitor within the arrangement and change when the resolution does, which is exactly when the layout should not be reused.
- **The HUD renders on a timer at ~30 Hz**, matching the UI drain rate. The telemetry engine polls at 200 Hz; repainting a window that fast would burn a core for frames nobody sees.

```csharp
// HudInterop — the two Win32 facts this feature rests on.
private const int GwlExStyle = -20;
private const int WsExTransparent = 0x00000020;
private const int WsExNoActivate = 0x08000000;

/// <summary>D3D exclusive fullscreen is running, so a topmost window will not be seen.</summary>
private const int QunsRunningD3dFullScreen = 3;

[DllImport("shell32.dll")]
private static extern int SHQueryUserNotificationState(out int state);
```

- [ ] Tests (headless): the toggle command is registered under `Live Compare`, capturable, not device-only; layout keys differ per resolution and round-trip through settings; a saved layout off every current screen is discarded rather than restored off-screen; the fullscreen notice text exists. Win32 calls themselves are not unit-tested — they are guarded and logged, like the WinUSB transport.
- [ ] UI review: HUD visible over the shell, locked and unlocked.

Commit: `feat(compare): transparent click-through HUD with a bindable toggle (#195)`

## Task 4 — Analysis view (#196)

**Files:** create `Features/Analysis/LapCorpusBrowser.cs`, `AnalysisController.cs`, `AnalysisView.cs`; modify `Shell/AppView.cs`, `MainWindow.cs`; test `AnalysisTests.cs`.

**Produces:**

**Decisions:**

- **A lap without a trace is still listed, marked with its tier and not selectable for channel overlay.** Hiding it would read as "that lap is gone".
- **The domain is `TrackPosition` here, not distance** — the Analysis view compares whole laps, and a full-lap axis in percent is the reading; distance is the HUD's local question.

## Task 5 — Lap files (#198)

**Files:** create `Features/SessionPlanning/LapTraceCodec.cs` (extracted), `Features/Sharing/SharedLap.cs`, `SharedLapFile.cs`, `SharedLapImporter.cs`; modify `LocalLapTraceStore.cs`, `LapHistoryModels.cs`; test `SharedLapTests.cs`.

**Produces:**
- `static class LapTraceCodec` — `void Write(Stream, LapChannelTrace)`, `LapChannelTrace? Read(Stream)` (the payload `LocalLapTraceStore` already writes, moved out unchanged)
- `sealed record LapProvenance(string SourceKind, string? SharedBy, string? ShareCode, DateTimeOffset? DrivenAt, DateTimeOffset SharedAt)`
- `sealed record SharedLap(LapProvenance Provenance, LapHistoryContext Context, int LapNumber, double LapTimeSeconds, LapChannelTrace Trace)` + `string Fingerprint`
- `static class SharedLapFile` — `Write(Stream, SharedLap)`, `SharedLap? Read(Stream)`, `const string Extension = ".sprintlap"`
- `LapHistoryOrigin.Shared`; `LapHistorySession.SharedFrom` / `SharedAt` / `ShareCode`
- `sealed class SharedLapImporter` — `SharedLapImportResult Import(SharedLap)`

**Decisions:**

- **One codec, three callers.** The local store, the lap file and the cloud blob all carry the same trace bytes. Two implementations of that layout would drift, and the drift would only show up on someone else's machine.
- **The file is magic + length-prefixed JSON provenance + the trace payload.** JSON for the header because it is small, human-inspectable and versionable; binary for the trace because it is not.
- **Import is never silent** (spec §2.7) — the driver sees what is being added and confirms it, the standard the planner's import prompt already set.
- **Dedupe on a fingerprint** of owner + context + lap number + lap time, so importing the same lap twice does not duplicate it.
- **A shared lap becomes its own single-lap history session** with `Origin = Shared`, so it flows through every existing corpus reader without any of them learning a new concept.

- [ ] Tests: round-trip including provenance and an unknown channel; truncated/garbage/unknown-version rejected with distinct reasons and no corpus write; import files a `Shared` session plus its trace; a second import of the same lap is a no-op; an imported lap appears in the corpus browser and is selectable as a Live Compare target.

Commit: `feat(sharing): a self-describing lap file and one receiving path (#198)`

## Task 6 — Cloud share codes (#197)

**Files:** create `api/Sprint.Api/Services/LapShareService.cs`, `app/Sprint.Desktop.Client/Features/Sharing/SprintCloudClient.cs`, `CloudSession.cs`; modify `api/Sprint.Api/Data/Entities.cs`, `SprintDbContext.cs`, `GraphQL/Query.cs`, `Mutation.cs`, `Services/UserService.cs`, `app/Sprint.Contracts/Auth.cs`, `Records.cs`, `packages/types`, `web/schema.graphql`; test `api/Sprint.Api.Tests` + desktop `CloudSharingTests.cs`.

**Produces:**
- `UserEntity.DisplayName`, `UserProfile.DisplayName`, mutation `setDisplayName`
- `LapTraceEntity { Id, OwnerId, ShareCode, Game, TrackCourse, CarModel, LapTimeSeconds, DrivenAt, Payload byte[], Revoked, CreatedAt }`, indexed on `ShareCode` (unique) and `OwnerId`
- `SharedLapDto`, `ShareLapInput`, `SharedLapSummary` in `Sprint.Contracts`
- Query `sharedLap(code)`, `mySharedLaps`; mutations `shareLap`, `revokeSharedLap`
- `SprintCloudClient` — GraphQL over `HttpClient`, JWT bearer

**Decisions:**

- **A share code is its own entity, not `InviteCodeEntity`** (spec §2.7). Engineer invites are bound to a running session and expire with it; a lap code must outlive every session and be revocable on its own.
- **Postgres blob, not InfluxDB.** Our x-axis is track position, not time; Influx would have to fake a time axis for an artifact that is neither streamed nor range-queried. Influx keeps its existing role for live session telemetry.
- **The payload is exactly the `.sprintlap` bytes.** Same format on disk and on the wire, so an exported file and a fetched lap cannot disagree.
- **The code is 128 bits of `RandomNumberGenerator`, base32, unguessable and not derived from the lap.** Deriving it would let anyone holding a lap's identity compute its code.
- **Revocation is a flag, not a delete**, so a revoked code reports "revoked" rather than "unknown" — three distinguishable failures: network, unknown code, revoked.
- **Only explicit shares upload** (spec §2.7). The corpus stays local; consent is per-lap and states what leaves the machine.
- The API uses `EnsureCreated`, so a new entity means existing dev databases need recreating. Call this out in the handoff.

- [ ] API tests: share mints a unique code; fetch by code returns the payload; revoke makes fetch fail as revoked, not unknown; another user cannot revoke; display name round-trips.
- [ ] Desktop tests: the client maps the three failure modes to distinct messages; a fetched lap goes through `SharedLapImporter` with provenance.
- [ ] `make schema`, then mirror contracts to `packages/types`.

Commit: `feat(cloud): per-lap share codes with revocation and a desktop client (#197)`
