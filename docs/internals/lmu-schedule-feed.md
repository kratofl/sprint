# Research: can Sprint safely automate an LMU weekly-schedule feed?

**Verdict: yes, with conditions.** A server-side feed in `api/` is feasible today by parsing the
first-party `racecontrol.gg` homepage, whose `robots.txt` imposes no restriction and which exposes
the live daily-race rotation in server-rendered HTML. There is **no official machine-readable
endpoint** — RaceControl is a server-rendered Rails app with no public JSON API.
The one clean, fully-normalized payload that exists (`api.lmuschedule.com/racingschedules`,
third-party) is **behind a deliberate `Referer` access control and must not be used without the
maintainer's permission** — which is worth asking for, because it carries fuel/tyre multipliers and
race-vs-session lengths that the RaceControl page does not.

All facts below were retrieved **2026-07-31, 22:28–22:33 UTC** unless stated otherwise. Everything
was a read-only `GET`. No authentication was attempted, no accounts created, no load testing.

---

## 1. Recommended source

### Primary: `https://www.racecontrol.gg/` (homepage HTML)

RaceControl is "the official platform of Le Mans Ultimate and rF2" (site tagline, homepage). The
homepage server-renders an **"Upcoming Daily Races"** block. At capture time it held 9 LMU entries
(plus 2 rF2 entries in a separate block), each with tier, series name, total duration, track, and
the next one or two start times.

Verbatim shape of one rendered entry (whitespace collapsed):

```
beginner
LMGTE Fixed
Duration    32 minutes
Track       Spa 2023
31 Jul at 10:30pm
31 Jul at 11:15pm
```

Why this is the primary recommendation:

- **First-party.** It is the operator's own site, not a mirror.
- **`robots.txt` does not restrict it.** `GET https://www.racecontrol.gg/robots.txt` → `200
  text/plain`; the entire body is the default Rails comment line
  `# See https://www.robotstxt.org/robotstxt.html for documentation on how to use the robots.txt file`
  with **no `Disallow` directives and no `Sitemap`**.
- **No auth, no gate.** Plain `GET` with any user agent returns `200`.
- **Precedent exists.** `lmuraces.com` already does exactly this (see §4), so the approach is
  demonstrably workable and already part of the ecosystem's normal traffic.

### Fallback if it disappears / the markup changes

1. **Ask first, then use `api.lmuschedule.com/racingschedules`** (§4.1). Strictly better data;
   strictly requires permission.
2. **`lmuhub.com` public HTML pages.** Its `robots.txt` and `llms.txt` explicitly *invite*
   retrieval of `/schedule`, `/daily-races/{beginner,intermediate,advanced}`, `/weekly-races`,
   `/special-events`, `/championship` — while *disallowing* `/api/`. HTML-only, and it is itself a
   derivative of RaceControl.
3. **Manual/degraded mode.** Ship the planner's Quick mode with a "schedule unavailable — enter it
   yourself" state and treat the feed as an enhancement, never a dependency.

### Confirmed dead ends on racecontrol.gg

| Probe | Result |
| --- | --- |
| `/daily_races`, `/races`, `/schedule`, `/api/daily_races`, `/api/v1/daily_races` | all `404` (972-byte HTML error page) |
| `GET /` with `Accept: application/json` | `406 application/json` |
| `application-*.js` bundle (719 KB) grepped for path literals | only `/cable`, `/xhr/users/calculate_age`, `/liveries/favourites` |

The bundle is Bootstrap + Rails UJS; the site does no XHR for race data. **There is no private JSON
API behind the frontend to discover** — the daily races are rendered server-side into the HTML.

`/events` is **not** the official rotation: it is the SimGrid-powered community/hosted-league
browser (854 results, "Powered By SimGrid"), i.e. user-created championships. Irrelevant to Quick
mode.

## 2. Terms findings

### 2.1 `racecontrol.gg/rules` — retrieved 2026-07-31

This page is the **competition** Terms & Conditions and Code of Conduct. Grepping the full text for
`scrap`, `crawl`, `robot`, `automat`, `bot`, `api`, `extract`, `harvest`, `redistribut`,
`commercial` surfaces **no clause governing website access, automated retrieval, or data reuse.**

The only automation-adjacent sentence concerns competition entries, not site access:

> "No applications from agents, third parties, organised groups or applications automatically
> generated by a computer will be accepted."

Governing law clause:

> "…shall be governed by Dutch law and the courts of The Netherlands shall have exclusive
> jurisdiction over any dispute arising from running the Le Mans Ultimate online."

The site's footer links to `/rules`, `/refund_policy`, and `https://motorsportgames.com/privacy-policy/`.
**It does not link to a site-wide Terms of Use.**

### 2.2 `https://motorsportgames.com/terms-conditions/` — retrieved 2026-07-31

This is Motorsport Games' website Terms of Use. Operative clauses, verbatim:

> "You agree not to use or launch any automated system, including without limitation, 'robots',
> 'spiders' or 'offline readers', to generate artificial views of Video Content, or to otherwise
> access the Motorsportgames.com Website in a manner that sends more request messages to the
> Motorsportgames.com servers in a given period of time than a human can reasonably produce in the
> same period by using a conventional on-line web browser."

> "Motorsportgames.com grants the operators of public search engines permission to use spiders to
> copy materials from the site for the sole purpose of and solely to the extent necessary for
> creating publicly available searchable indices of the materials, but not caches or archives of
> such materials."

> "You agree not to distribute in any medium any part of the Motorsportgames.com Website, including
> but not limited to User Submissions (defined below), without Motorsportgames.com's prior written
> authorization."

> "You agree not to use the Motorsportgames.com Website … for any commercial use, without the prior
> written authorization of Motorsportgames.com."

Scope clause, verbatim:

> "These Terms of Use apply to all users of the Motorsportgames.com Website, including users who
> contribute video content, information, and other materials or services on the Website."

No effective/last-updated date was present.

**Reading.** The automated-access clause is **rate-based**, not a blanket prohibition: a poll of a
few requests per day is comfortably "less than a human can reasonably produce … using a conventional
web browser". The clauses that actually bite are *distribution* and *commercial use*. **Whether
these terms reach `racecontrol.gg` at all is unresolved** — they are scoped by their own wording to
"the Motorsportgames.com Website", and racecontrol.gg does not incorporate them by reference. That
is a human/legal call, not something this research can settle (§6).

## 3. Payload field map

### 3.1 What RaceControl's homepage actually gives you

| Field | Present | Notes |
| --- | --- | --- |
| Tier | ✅ | `beginner` / `intermediate` / `advanced` |
| Series name | ✅ | e.g. `LMGTE Fixed`, `ELMS Super 60`, `WEC-Xperience` |
| Track | ✅ | Display string only: `Spa 2023`, `Cot A Wec 2024`, `Daytona 2026` |
| Duration | ⚠️ | `32 minutes` / `1h 12 minutes` — **total session-set time, not race length** (see below) |
| Start times | ⚠️ | Next 1–2 slots only, rendered `31 Jul at 10:30pm` — **no timezone marker in the text**; matched UTC at capture time, but this must be treated as unverified rendering behaviour |
| Car classes | ❌ | Implied by series name only |
| Practice / qualifying / race split | ❌ | — |
| Time- vs lap-based | ❌ | — |
| Fuel / tyre multipliers | ❌ | — |
| Fixed vs open setup | ❌ | Implied by `"Fixed"` in some series names only |
| Full week ahead | ❌ | Only the imminent window |

The **duration is total session time**, proven by cross-checking against §3.2:
`LMGTE Fixed` shows `32 minutes` where the underlying data is practice 2 + qualifying 5 + race 20;
`ELMS Super 60` shows `1h 12 minutes` where the race itself is 60. Consistently
`displayed ≈ practice + qualifying + race + ~2`. **Do not feed this number into a fuel calculation.**

### 3.3 Gaps against what the Session Planner needs

| Planner input | RaceControl HTML | lmuschedule payload |
| --- | --- | --- |
| Track | display string — needs a mapping table to Sprint's track ids | display string — same problem |
| Car / class | ❌ (infer from series name) | ✅ `carClasses[]` — still needs mapping to Sprint's class ids |
| Time- vs lap-based | ❌ | ⚠️ **implicitly time-based only.** `raceLength` is minutes; there is **no lap-count field**, so a lap-based event cannot be represented at all |
| Race duration | ❌ (total session time only) | ✅ `raceLength` |
| Fuel multiplier | ❌ | ✅ `fuelUsage` — **directly feeds Sprint's fuel maths** |
| Tyre wear multiplier | ❌ | ✅ `tireWear` |
| Tyre set limit | ❌ | ✅ `limitedTires` / `tiresAvailable` |
| Session structure | ❌ | ✅ `practiceLength` / `qualifyingLength` / `raceLength` |
| Start times, full week | ❌ (next 1–2 slots) | ✅ `times[]` in UTC for the whole week |
| Timezone handling | ⚠️ unmarked local rendering | ✅ unambiguous ISO-8601 `Z` |

**Absent from both:** weather and time-of-day settings, pit/refuelling rules, per-slot server or
split identity, and any lookahead beyond the current week.

The two rows that matter most — `fuelUsage` and `raceLength` — are exactly the ones the free source
lacks. That is the strongest argument for spending a human email on §6.2.

## 4. Third-party sources, ranked

### 4.1 `lmuschedule.com` — best data, **gated, needs permission**

Angular SPA on S3/CloudFront. Its bundle contains
`{production:!0, apiUrl:"https://api.lmuschedule.com"}` and a service that does
`GET ${apiUrl}/racingschedules` and reads `response.body`.

The API is an AWS API Gateway (`us-east-1`) with a **resource policy keyed on the `Referer`
header**. Probed:

| Request | Result |
| --- | --- |
| No `Referer` (any UA, incl. `Mozilla/5.0`) | `403` `{"message":"User: anonymous is not authorized to perform: execute-api:Invoke … because no resource-based policy allows the execute-api:Invoke action"}` |
| `Referer: https://example.com/` | `403` |
| Empty `Referer` | `403` |
| `Referer: https://www.lmuschedule.com/` | `200`, full payload |

This is a **deliberate, domain-specific technical access control**, not an accident. Sending a
forged `Referer` to obtain the data would be circumventing it. **Sprint must not do that.** The
correct move is to ask (§6.2); the maintainer is contactable via
`https://buymeacoffee.com/lmuschedule`, linked from the site.

`https://www.lmuschedule.com/assets/updated-date.txt` returns `Jul 28` — i.e. the dataset is
**hand-curated weekly by the maintainer**, refreshed on the Tuesday rollover. That is both a
strength (it is accurate, per §3.2) and a risk (it depends on one person doing it each week).

### 4.2 `lmuraces.com` — a working precedent, not a source

The page is static HTML whose inline script does:

```js
const res = await fetch('https://lmu-proxy.rnlnortherns.workers.dev/');
… if (text.length > 1000 && (text.includes('lmu_logo') || text.includes('racecontrol'))) html = text;
… parseRaces(html);   // regex over the RaceControl homepage markup
```

It is a Cloudflare Worker CORS proxy in front of `racecontrol.gg`, plus a regex parse of the
homepage. **Its data is strictly a subset of source 1 with an extra hop.** Useful only as evidence
that homepage-parsing is an accepted, working pattern in this ecosystem. Sprint's `api/` would do
the same thing without needing the proxy.

### 4.3 `lmuhub.com` — HTML sanctioned, API forbidden

`robots.txt` disallows `/api/` for everyone including named AI crawlers; `llms.txt` explicitly names
the public pages as preferred retrieval targets and says not to use private API routes. Reasonable
HTML fallback; advertises a `/championship` week-by-week calendar that may carry lookahead the other
sources lack (**not verified** — see §7).

### 4.4 `lmuportal.com` — API forbidden

`robots.txt` disallows `/api/`. Not usable as a feed.

### 4.5 `lmuzone.com` — technically open, practically not usable

`robots.txt` permits everything, but the SPA talks **directly to a Supabase project**
(`https://cnqtrcfwnfihwxprtspz.supabase.co`) using an anon key embedded in the JS bundle. Using that
endpoint means using someone else's credentials and burning their quota. Not appropriate without
permission, regardless of what robots.txt says.

**Ranking by stability + licence clarity:**
`racecontrol.gg` (first-party, unrestricted) > `lmuschedule.com` (best payload, gated — ask) >
`lmuhub.com` HTML (explicitly invited) > `lmuraces.com` (derivative) > `lmuportal.com` /
`lmuzone.com` (blocked or credential-bound).

## 5. Cadence, poll interval, and caching

### Observed cadence

The rotation is **weekly, rolling over Tuesday ≈ 10:00 UTC.** Evidence from the payload's `times[]`
arrays (hard data, not a forum claim): every Daily Races series begins its week at
`2026-07-28T10:00Z`–`10:55Z` (a Tuesday) and its final slot lands `2026-08-04T08:55Z`–`09:55Z` (the
following Tuesday). `updated-date.txt` reading `Jul 28` — also a Tuesday — corroborates it.

Secondary claims disagree on the hour: `lmuraces.com` states "resets every Tuesday at 10am UTC";
another search-surfaced summary said Tuesdays 12:00 UTC. **The 10:00 UTC boundary is what the data
supports**; treat the exact minute as approximate and detect the rollover rather than assuming it.

Within a week: `Daily Races` repeat every 45–60 minutes across all 7 days (112–224 slots per
series). `Weekly Races`, `Special Event`, and `Championship Races` occupy day subsets
(`days: ["T","W","R","M"]` etc.) with a handful of slots each.

**Only the current week is published anywhere I could reach.** Championship records carry
`weekNumber` / `rounds` / `isCurrentWeek`, implying a season calendar exists, but no future-week
`times[]` were exposed. There is **no lookahead**, so the planner cannot pin a plan to next week's
event.

### Recommended polling

**Hourly is roughly 40× more often than the data changes.** Recommended:

- **Baseline: every 6 hours** (4 requests/day). The dataset is weekly; this only exists to catch
  mid-week corrections.
- **Rollover burst: every 15 minutes from Tuesday 09:30 to 11:30 UTC** (8 requests), stopping early
  once the parsed content changes. Covers the reset without hammering.
- **Total ≈ 12 requests/day, ≈ 1.6 MB/day.** That is unambiguously below "more than a human can
  reasonably produce using a conventional web browser".
- **One in-flight request at a time**, no concurrency, no retry storms.
- Identify honestly: a descriptive `User-Agent` naming Sprint with a contact URL. Do **not**
  masquerade as a browser, and do **not** send a `Referer` you are not entitled to.

### Caching behaviour

RaceControl response headers (homepage):

```
Cache-Control: max-age=0, private, must-revalidate
Etag: W/"feedbcb285c37099c0238a507c665160"
Vary: Accept
Server: Heroku
```

**Conditional GET buys nothing.** Re-requesting ~4 minutes later with
`If-None-Match: W/"feedbcb…"` returned **`200`, not `304`**, with a new ETag
(`W/"28f541fabff7b22af6a6a722b4b83495"`) and a different `Content-Length` (137378 → 137120). The
page embeds live countdown state, so the ETag rotates continuously. Budget a full ~135 KB fetch per
poll and **do the caching on Sprint's side**:

- `api/` parses once, stores the normalized week, and serves desktop clients from its own cache with
  its own stable `ETag` / `Cache-Control` keyed on the parsed content hash.
- TTL until the next expected Tuesday 10:00 UTC rollover, refreshed by the poller.
- Desktop clients poll `api/`, never the third party — as the design assumption stated. One
  well-behaved caller, and a source change is a server fix.
- Persist the last good parse. If a poll fails or parses to zero races, **serve the last good week
  and mark it stale**; never blank the planner and never silently show an outdated week as current.

### Failure modes observed

- Unknown paths return **`404` with a 972-byte HTML error page**, not JSON. Error handling must key
  on **status code**, not body shape.
- `Accept: application/json` on a valid path returns **`406`**.
- No `Retry-After`, no `X-RateLimit-*`, no `429` observed. Rate-limit behaviour was **not probed** —
  probing it would mean load testing, which was out of scope.
- Heroku router in front; expect the usual `503`/`H12` class on their side. Exponential backoff on
  `5xx`; **never** auto-retry a `4xx`.
- `lmuzone.com/schedule` was served from Vercel cache with `Age: 1266600` (~14.7 days) and
  `Last-Modified: 2026-07-17` — that is the static SPA shell, not stale data, but it is a reminder
  that CDN-fronted shells tell you nothing about data freshness.

## 6. Open risks and human decisions

1. **Legal scope is unresolved and is not an engineering call.** Motorsport Games' Terms of Use are
   self-scoped to "the Motorsportgames.com Website" and are not incorporated by reference on
   racecontrol.gg. *If* they were held to apply, the "distribute in any medium any part of the
   Website … without prior written authorization" and "no commercial use" clauses would arguably
   cover Sprint re-serving RaceControl-derived schedule data to its users. The low-rate polling
   itself is clearly fine under their rate-based automation clause. **A human should decide whether
   to proceed on the reading that these terms do not bind racecontrol.gg, or to ask first** via
   `support.racecontrol.gg`. Asking also opens the door to a sanctioned feed.

2. **Ask the `lmuschedule.com` maintainer.** Highest-value human action available. Their payload is
   a superset of everything the planner needs, already normalized, already proven accurate against
   the official site, and it carries `fuelUsage` / `tireWear` / `raceLength` that RaceControl's page
   does not. Ask for an allowlist entry or a keyed endpoint; offer attribution and a
   once-per-6-hours cap. Contact: `https://buymeacoffee.com/lmuschedule`. **Under no circumstances
   spoof the `Referer` while waiting for an answer.**

3. **HTML parsing is presentation-coupled.** Any RaceControl redesign breaks the parse, possibly
   silently (a regex that matches nothing looks identical to "no races scheduled"). Mitigation: a
   sanity assertion — a parse yielding 0 LMU daily races is an *error*, not an empty week — plus an
   alert and an explicit "schedule unavailable" state in the planner UI.

4. **`Duration` on the homepage is total session time, not race length.** Feeding it into a fuel or
   stint calculation would be wrong by 30–60%. Either decompose it (not possible from the page
   alone) or do not surface duration-derived numbers until source §4.1 is licensed.

5. **No lap-based representation exists in any source.** If LMU ever runs a lap-count event, the
   feed cannot express it. The Sprint-side model should carry an explicit "time-based" discriminator
   rather than assuming it.

6. **Name normalization is unsolved work.** `"Cot A Wec 2024"`, `"Spa 2023"`, `"Daytona Intl.
   Speedway (Road Course)"` are display strings that must be mapped to Sprint's track model, and
   `"LMP2 (ELMS)"` / `"HYP"` / `"GTE"` to Sprint's class model. This mapping table is hand-built and
   needs maintenance every time LMU adds content.

7. **Single-maintainer risk** applies to every third-party option, including the best one.

8. **No lookahead.** Quick mode can pin to *this* week only. If the planner's UX implies future
   planning, that expectation has to be managed.

## 7. Explicitly not verified

- Whether `racecontrol.gg` has any site-wide Terms of Use at all. Only `/rules` (competition T&C),
  `/refund_policy`, and a link to the MSG privacy policy were found.
- Whether the Motorsport Games Terms of Use apply to `racecontrol.gg`. The scope clause names only
  "the Motorsportgames.com Website".
- Whether mid-week schedule corrections happen. No evidence either way; the 6-hour baseline poll
  exists precisely because this is unknown.
- Whether any source publishes more than one week ahead. `lmuhub.com/championship` advertises a
  "week-by-week LMU online championship calendar" in its `llms.txt`; **that page was not
  retrieved.**
- Terms-of-use / licence pages for `lmuschedule.com`, `lmuhub.com`, `lmuportal.com`, `lmuzone.com`,
  `lmuraces.com`. Only their `robots.txt` and `llms.txt` were examined. `lmuschedule.com`'s
  about/contact page was not retrieved; the Buy-Me-A-Coffee link came from its JS bundle.
- Rate limits, `Retry-After` behaviour, and `429` handling on `racecontrol.gg` — deliberately not
  probed, since establishing them requires load testing.
- The timezone the RaceControl homepage renders start times in. `31 Jul at 10:30pm` matched UTC
  at capture, but no `<time>` element, `datetime` attribute, or timezone marker was confirmed, and
  the site may localize per client. **A parser must resolve this before trusting the times** —
  cross-referencing against the known UTC slot pattern is the safer route.
- Whether RaceControl exposes the weekly/special/championship rotation anywhere on its own site.
  Only the imminent daily-race window was found on the homepage; no full-schedule page was located.
- The in-game localhost REST service (`HttpServer.WindowsDesktop.dll`). The game was not running, so
  no endpoint was enumerated. It remains useless for planning while the game is closed regardless.
- Ownership and terms of the `lmu-proxy.rnlnortherns.workers.dev` Cloudflare Worker.
